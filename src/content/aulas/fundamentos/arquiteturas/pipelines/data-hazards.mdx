# AULA 02 — CONFLITOS DE DADOS (DATA HAZARDS)

## 1. INTRODUÇÃO

Na aula anterior, estudamos o pipeline de 5 estágios e vimos como ele permite que várias instruções sejam executadas simultaneamente, aumentando o throughput do processador. Vimos que, em um pipeline ideal, uma instrução é concluída a cada ciclo.<br><br>

Mas o mundo real não é tão simples. Há momentos em que o pipeline **precisa parar** — uma instrução não pode prosseguir porque depende de um resultado que ainda não foi calculado por uma instrução anterior. É como um operário em uma linha de montagem que não pode continuar porque a peça que ele precisa ainda está sendo feita pelo operário anterior.<br><br>

Esses momentos de parada são chamados de **conflitos de dados (data hazards)**. Eles são a principal razão pela qual o pipeline real nunca atinge o desempenho teórico máximo.<br><br>

Imagine que você está cozinhando várias receitas ao mesmo tempo. Uma receita diz "adicione o molho que você preparou na receita anterior". Se você ainda não terminou a receita anterior, você precisa esperar — não pode continuar. O pipeline da CPU enfrenta exatamente o mesmo problema.<br><br>

Nesta aula, vamos estudar os conflitos de dados: o que são, como identificá-los, os diferentes tipos (RAW, WAR, WAW), e como o processador lida com eles usando técnicas como **stalls** e **forwarding**.

## 2. O QUE SÃO CONFLITOS DE DADOS?

### 2.1 Definição

> "Conflito de dados (Data Hazard) é uma situação no pipeline onde uma instrução depende do resultado de uma instrução anterior que ainda não foi concluída, forçando o pipeline a parar (stall) ou utilizar técnicas de mitigação como forwarding."

### 2.2 Características principais

| Característica | Descrição |
|---------|----------|
| **O que causa** | Dependência entre instruções (uma precisa do resultado da outra) |
| **Quando ocorre** | Quando a distância entre instruções é menor que o tempo de execução da instrução anterior |
| **Consequência** | Pipeline stall (pausa) ou forwarding (encaminhamento) |
| **Tipos** | RAW (Read After Write), WAR (Write After Read), WAW (Write After Write) |

### 2.3 Analogia

Os conflitos de dados são como **receitas de cozinha**:

- **RAW (Read After Write):** "Adicione o molho que você preparou na receita anterior." Você precisa esperar o molho ficar pronto antes de adicioná-lo.
- **WAR (Write After Read):** "Leia a quantidade de farinha, depois escreva o resultado na mesma variável." A ordem importa.
- **WAW (Write After Write):** "Escreva o resultado na variável X, depois escreva outro resultado na mesma variável." A última escrita deve ser a que prevalece.

## 3. OS TRÊS TIPOS DE CONFLITOS DE DADOS

### 3.1 Tipos de dependências

| Tipo | Nome | Descrição | Exemplo |
|---------|---------|---------|---------|
| **RAW** | Read After Write | Instrução lê um valor que uma instrução anterior vai escrever | `ADD R1, R2, R3` / `SUB R4, R1, R5` |
| **WAR** | Write After Read | Instrução escreve em um local que uma instrução anterior leu | `SUB R4, R1, R5` / `ADD R1, R2, R3` |
| **WAW** | Write After Write | Duas instruções escrevem no mesmo local | `ADD R1, R2, R3` / `SUB R1, R4, R5` |

**Exemplo:**

Instrução 1: SUB R4, R1, R5    ; R4 = R1 - R5 (lê R1)
Instrução 2: ADD R1, R2, R3    ; R1 = R2 + R3 (escreve em R1)
</pre>

**Problema:** A instrução 2 escreve em R1 antes que a instrução 1 tenha lido o valor antigo de R1.

**Observação:** WAR é menos comum e geralmente não ocorre em pipelines in-order.

**Exemplo:**

Instrução 1: ADD R1, R2, R3    ; R1 = R2 + R3
Instrução 2: SUB R1, R4, R5    ; R1 = R4 - R5

**Problema:** As duas instruções escrevem em R1. O valor final deve ser da instrução 2.

**Observação:** WAW também é menos comum e geralmente não ocorre em pipelines in-order.

## 4. COMO O PIPELINE LIDA COM CONFLITOS DE DADOS?

### 4.1 Método 1: Stalling (Pausa)

A forma mais simples de lidar com data hazards é **parar o pipeline** até que o dado necessário esteja disponível.

**Como funciona:**
1. A CPU detecta que a instrução 2 precisa do resultado da instrução 1.
2. A CPU insere "bolhas" (bubbles) no pipeline — estágios vazios.
3. A instrução 2 fica presa no estágio ID até que o dado esteja disponível.
4. Quando o dado está disponível, a instrução 2 prossegue.

**Exemplo:**

<summary> **Stalling no pipeline**</summary>
    <pre style="color: white; background: #0a0f1e; padding: 1rem; border-radius: 8px; font-family: monospace; font-size: 0.85rem; border: 1px solid rgba(255,255,255,0.08); overflow-x: auto;">
Ciclo:  1    2    3    4    5    6    7    8
I1:    [IF] [ID] [EX] [MEM] [WB]
I2:         [IF] [ID] [STALL] [STALL] [ID] [EX] [MEM] [WB]
                                        ↑
                              Esperou até R1 estar disponível
    </pre>
</details>

**Desvantagem:** Perda de desempenho (ciclos desperdiçados).

### 4.2 Método 2: Forwarding (Encaminhamento)

O forwarding (ou bypass) é uma técnica que **envia o resultado diretamente** da saída de um estágio para a entrada de outro, sem esperar a escrita no registrador.

**Como funciona:**
1. O resultado da ULA no estágio EX é enviado diretamente para o estágio ID (ou EX) da próxima instrução.
2. A instrução dependente recebe o valor **antes** de ser escrito no registrador.
3. O pipeline não precisa parar.

**Exemplo (com forwarding):**

<details>
<summary> **Forwarding no pipeline**</summary>
    <pre style="color: white; background: #0a0f1e; padding: 1rem; border-radius: 8px; font-family: monospace; font-size: 0.85rem; border: 1px solid rgba(255,255,255,0.08); overflow-x: auto;">
Ciclo:  1    2    3    4    5    6
I1:    [IF] [ID] [EX] [MEM] [WB]
I2:         [IF] [ID] [EX] [MEM] [WB]
                   ↑
              Forwarding: resultado de I1 (EX) vai direto para I2 (EX)
    </pre>
</details>

**Vantagem:** Sem stalls, pipeline continua cheio.

## 6. DETECÇÃO DE DATA HAZARDS

### 6.1 Como a CPU detecta conflitos

A CPU usa a **unidade de detecção de hazards** para identificar conflitos:

1. **Compara registradores:** Verifica se o registrador destino de uma instrução no pipeline é o mesmo que o registrador fonte de uma instrução posterior.
2. **Verifica estágios:** Determina se o resultado já está disponível ou se é necessário stall.
3. **Decide ação:** Stalling, forwarding, ou ambos.

### 6.2 Tabela de decisão

| Situação | Ação |
|---------|---------|
| Instrução em EX usa resultado de instrução em EX | Forwarding |
| Instrução em EX usa resultado de instrução em MEM | Forwarding |
| Instrução em EX usa resultado de instrução em WB | Sem ação (já está disponível) |
| Instrução em ID usa resultado de instrução em EX | Stall + Forwarding |
| Load → Instrução seguinte | Stall + Forwarding |

## 7. APLICAÇÕES REAIS

| Aplicação | Como lida com data hazards |
|---------|----------|
| **Processadores modernos** | Forwarding + Branch Prediction + Out-of-Order |
| **Processadores simples (RISC)** | Stalling + Forwarding simples |
| **Microcontroladores** | Pipeline com forwarding limitado |
| **Processadores embarcados** | Pipeline simples, stall em conflitos |

**Exemplo prático:** O compilador pode reordenar instruções para minimizar data hazards. Isso é chamado de **otimização de código**.

<details>
<summary>💡 Ver resposta</summary>

**Resposta:**
- **Stalling:** Pausa o pipeline, inserindo bolhas. Perde ciclos de execução.
- **Forwarding:** Envia o dado diretamente, sem pausar o pipeline. Não perde ciclos.

**Conclusão:** Forwarding é preferível por manter o pipeline cheio e maximizar o throughput.

**Explicação:** Stalling é usado quando forwarding não é possível (ex: após um load).

**Enunciado:** Por que um load (LDR) seguido de um uso imediato do valor carregado causa um stall mesmo com forwarding?

<details>
<summary>💡 Ver resposta</summary>

**Solução:** O pipeline precisa stall por 1 ciclo até que o dado esteja disponível no estágio MEM, e então fazer forwarding para a instrução seguinte.

**Explicação:** Esse é o chamado "load-use hazard" — uma das principais fontes de stalls em pipelines.

> Conflitos de dados são os principais vilões do pipeline. Quando uma instrução depende do resultado de outra, o pipeline precisa parar (stall) ou usar forwarding para passar o dado diretamente. O tipo mais comum é o RAW (Read After Write), e técnicas como forwarding e otimização de código são essenciais para manter o pipeline ocupado e o desempenho alto. Os conflitos de dados são uma das principais razões pelas quais o pipeline real nunca atinge o desempenho teórico máximo. Entender como eles funcionam e como são mitigados é essencial para compreender o design de processadores e a otimização de código em baixo nível.

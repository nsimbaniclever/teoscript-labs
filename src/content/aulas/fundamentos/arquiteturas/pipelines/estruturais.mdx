# CONFLITOS ESTRUTURAIS

## 1. INTRODUÇÃO

Nas duas últimas aulas, estudamos o pipeline e seus conflitos de dados — situações onde uma instrução depende do resultado de outra. Vimos que esses conflitos podem ser resolvidos com stalls e forwarding.<br><br>

Mas há outro tipo de conflito que pode parar o pipeline: os **conflitos estruturais**. Eles ocorrem quando dois estágios diferentes do pipeline precisam usar o **mesmo recurso físico** ao mesmo tempo. É como dois operários em uma linha de montagem que precisam usar a mesma ferramenta ao mesmo tempo — um deles precisa esperar.<br><br>

Imagine uma cozinha com apenas um forno. O chef está assando um bolo (estágio EX), e o ajudante precisa assar um pão (estágio MEM). Os dois não podem usar o forno ao mesmo tempo. Alguém precisa esperar. Isso é um conflito estrutural.<br><br>

Os conflitos estruturais são mais fáceis de resolver que os conflitos de dados: basta **duplicar o recurso** ou **escalonar o acesso**. Mas eles são um lembrete importante de que o pipeline não é apenas sobre organização — é também sobre recursos físicos limitados.<br><br>

Nesta aula, vamos estudar os conflitos estruturais: o que são, como identificá-los, como resolvê-los, e por que eles são menos comuns em processadores modernos.

## 2. O QUE SÃO CONFLITOS ESTRUTURAIS?

### 2.1 Definição

> "Conflito estrutural (Structural Hazard) é uma situação no pipeline onde dois estágios diferentes precisam usar o mesmo recurso físico (memória, barramento, unidade funcional) ao mesmo tempo, forçando um dos estágios a esperar."

### 2.2 Características principais

| Característica | Descrição |
|---------|----------|
| **O que causa** | Recursos físicos compartilhados entre estágios |
| **Quando ocorre** | Quando dois estágios tentam acessar o mesmo recurso no mesmo ciclo |
| **Consequência** | Pipeline stall (um estágio espera) |
| **Solução** | Duplicar recursos, escalonar acesso, ou stalls |

### 2.3 Analogia

Os conflitos estruturais são como **uma sala de espera com apenas uma cadeira**. Duas pessoas chegam ao mesmo tempo e querem sentar. Alguém precisa esperar.

- **Harvard architecture:** Memória de instrução e memória de dados separadas.

### 3.2 Conflito no barramento

O barramento de dados é compartilhado entre vários componentes. Conflitos ocorrem quando múltiplos acessos são solicitados.

**Exemplo:**
- IF quer buscar instrução.
- MEM quer ler/escrever dados.
- DMA (Direct Memory Access) quer transferir dados.

**Solução:** Priorização e arbitragem.

### 3.3 Conflito em unidades funcionais

Conflitos ocorrem quando duas instruções precisam da mesma unidade funcional ao mesmo tempo.

**Exemplo:**
- Duas instruções de multiplicação consecutivas precisam usar a mesma unidade de multiplicação.

**Solução:** Múltiplas unidades funcionais ou pipeline de unidades funcionais.

### 3.4 Conflito em registradores

Conflitos ocorrem quando múltiplos estágios precisam acessar o banco de registradores ao mesmo tempo.

**Exemplo:**
- ID lendo registradores.
- WB escrevendo em registradores.

**Solução:**
- Leitura e escrita simultâneas (se o banco de registradores suportar).
- Escalonamento de acesso.

## 4. SOLUÇÕES PARA CONFLITOS ESTRUTURAIS

### 4.1 Duplicação de recursos

A solução mais simples: **duplicar o recurso problemático**.

| Recurso problemático | Solução |
|---------|----------|
| **Memória única** | Memória de instrução (I-cache) e memória de dados (D-cache) |
| **Barramento único** | Barramentos separados para instrução e dados |
| **Unidade funcional** | Múltiplas unidades (ex: 2 multiplicadores) |
| **Banco de registradores** | Leitura e escrita simultâneas |

### 4.2 Pipeline stalls (pausas)

Quando duplicar recursos não é viável, o pipeline pode pausar (stall) um dos estágios.

**Como funciona:**
1. Detecta-se que o recurso está ocupado.
2. O estágio que precisa do recurso é pausado (stall).
3. Os estágios anteriores também são pausados (para não perderem dados).
4. Quando o recurso fica disponível, o pipeline prossegue.

### 4.3 Escalonamento de acesso

O acesso ao recurso é organizado em diferentes ciclos.

**Exemplo:** Memória de ciclo único com acesso alternado:
- Ciclo par: IF (busca instrução)
- Ciclo ímpar: MEM (acessa dados)

### 4.4 Projeto sem conflitos estruturais

A melhor solução é **projetar o pipeline para que não haja conflitos estruturais**.

**Regras de projeto:**
1. Cada estágio usa recursos diferentes.
2. Recursos compartilhados são duplicados ou escalonados.
3. O pipeline é projetado para que, em cada ciclo, nenhum estágio precise do mesmo recurso que outro.

## 6. CONFLITOS ESTRUTURAIS VS DATA HAZARDS

| Característica | Conflito Estrutural | Data Hazard |
|---------|---------|---------|
| **Causa** | Recursos compartilhados | Dependência de dados |
| **Quem sofre** | Dois estágios precisam do mesmo recurso | Instrução precisa de dado não disponível |
| **Solução** | Duplicação de recursos | Forwarding, stalls |
| **Frequência** | Menos comum hoje | Muito comum |
| **Custo de mitigação** | Mudança de hardware (mais caro) | Técnicas de pipeline (menos caro) |

## 7. APLICAÇÕES REAIS

| Aplicação | Como lida com conflitos estruturais |
|---------|----------|
| **Processadores modernos** | Harvard cache (I-cache e D-cache separadas) |
| **Processadores simples** | Uma única memória, stalls para resolver |
| **Microcontroladores** | Memória única, stalls |
| **Processadores embarcados** | Pode usar memória única com stalls |
| **GPUs** | Múltiplas unidades funcionais, alta paralelização |

**Exemplo prático:** Processadores Intel Core têm caches L1 separadas para instrução (I-cache) e dados (D-cache). Isso elimina o conflito estrutural mais comum.

**Enunciado:** Por que duplicar recursos é uma solução cara para conflitos estruturais?

**Resposta:** Duplicar recursos aumenta o custo de fabricação, o consumo de energia e a área do chip.

**Explicação:** Cada unidade adicional (ex: multiplicador extra) ocupa espaço no chip, consome energia e custa para ser fabricada. Por isso, os projetistas equilibram o número de unidades com as necessidades do pipeline.

<details>
<summary>📗 Exercício 7 — Conflito estrutural vs Data Hazard (Difícil)</summary>

**Enunciado:** Qual a principal diferença entre um conflito estrutural e um data hazard?

<details>
<summary>💡 Ver resposta</summary>

**Resposta:**
- **Conflito estrutural:** Dois estágios precisam do mesmo **recurso físico** (memória, barramento, unidade funcional).
- **Data hazard:** Uma instrução precisa do **dado** que outra instrução ainda não produziu.

**Explicação:** Um é problema de hardware/recursos; o outro é problema de dependência de dados.
</details>

<summary>📗 Exercício 8 — Projetando sem conflitos (Desafio)</summary>

**Enunciado:** Como um projetista de processador pode garantir que não haja conflitos estruturais em um pipeline?

<details>
<summary>💡 Ver resposta</summary>

**Resposta:**

2. **Escalonar acesso:** Organizar o uso do recurso em diferentes ciclos.
3. **Projetar estágios independentes:** Cada estágio usa recursos diferentes.
4. **Analisar o pipeline:** Identificar todos os potenciais conflitos e resolvê-los no design.

**Explicação:** Um bom projeto de pipeline prevê e elimina conflitos estruturais antes que eles ocorram, usando as técnicas acima.

> Conflitos estruturais são um lembrete de que o pipeline não é apenas sobre organização — é também sobre recursos físicos. Quando dois estágios precisam do mesmo recurso ao mesmo tempo, o pipeline precisa parar. A solução mais elegante é duplicar o recurso (como as caches I e D separadas), mas quando isso não é viável, stalls resolvem o problema. Os conflitos estruturais são menos comuns em processadores modernos porque os projetistas investem em duplicação de recursos — especialmente memória separada para instrução e dados. Entretanto, eles continuam sendo uma consideração importante no design de processadores, especialmente em sistemas embarcados onde área e custo são limitados.
